# Model card: the target detector

A model card is what "model governance" means in practice: a short document that
says what a model is for, what it was trained on, what it measured, and how it
fails. FAA Part 108 is moving compliance responsibility onto operators, and the
industry advice is to document this before it is mandatory. This is that document
for the detector in this repository.

## Model

| Field | Value |
|---|---|
| Task | single-class object detection, nadir camera, 0.3 m coloured cubes |
| Architecture | YOLO11n, fine-tuned |
| Input | 640×640, letterboxed from 1280×960 |
| Output | boxes in source-frame pixels, decoded by `perception/yolo.py` |
| Classes | 1 (`target`) |
| Export | ONNX, opset 12, simplified, batch 1 |
| Baseline alternative | HSV colour threshold, `perception/color_baseline.py` |

## Intended use

- Detection of the coloured target cubes in the Gazebo world shipped with this
  repository, from a nadir camera at roughly 5 m.
- Research, teaching and portfolio use, in simulation.
- As one input to a control loop that has its own geofence, timeout and
  confirmation rules.

## Out of scope

- **Real aircraft or real imagery.** Nothing here has flown outdoors.
- Other object classes, other altitudes, oblique cameras, poor light, motion
  blur, rain, dust.
- Safety-critical decisions. The loop is a demonstration; the failsafes are PX4's
  and are not certified.
- Claiming generalisation: the fine-tune saw 59 frames from two flights of one
  target.

## Training data

| Source | Count | Notes |
|---|---|---|
| Synthetic nadir images (`scripts/make_synthetic_dataset.py`) | 500 train / 100 held out | seeded, grey ground with noise, squares with rotation, shading, shadow |
| Background frames (`scripts/harvest_negatives.py`) | 45 | real Gazebo frames with no target, harvested from the demo GIF |
| Real frames, geometry-labelled (`scripts/label_real_frames.py`) | 59 train / 31 held out | labels come from the colour baseline + known 0.3 m cube geometry |

Provenance: every one of those files is generated by a script in this repository
with a fixed seed or from a committed asset. There is no scraped data.

## Known failure modes

| Failure | Symptom | Mitigation in this repository |
|---|---|---|
| Domain shift | a synthetic-only model predicts boxes half the frame wide | real-frame fine-tune; the box size is checked, not just mAP |
| Shadow confusion | the model also fires on the vehicle's own shadow | hard negatives from real frames |
| Edge truncation | a target leaving the frame loses its track id | documented; the mission re-acquires after a search |
| Channel-order decode | a channel-first export decoded as rows of boxes | fixed; `tests/test_yolo.py` |
| Attitude | a level-camera projection loses ~0.9 m per 10° of pitch | roll/pitch compensated; `tests/test_projection_attitude.py` |

## Governance

- **Version**: the model file is git-ignored; the generating scripts, seeds,
  training command and export flags are in `docs/model.md` and the changelog.
- **Evaluation protocol**: `docs/experiment-protocol.md`; metrics come from
  `make bench`, never from a number typed by hand.
- **Change control**: a new model is only reported if it is re-flown, and the
  previous rows stay in `results/`.
- **Provenance**: `results/` holds the evidence for every number above.

## What this card does not do

It does not certify anything. It is a description written by the same person who
trained the model, in a repository with no independent review, and it should be
read as such.
