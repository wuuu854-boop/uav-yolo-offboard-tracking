# Repeatability of the recent doorway tasks

A single SITL pass is not evidence of robustness. The retained suite repeats the
doorway missions, restarting the simulator between runs, and keeps every failure
that led to a configuration change. The final target1 sample is **n=20**, and it
changed the conclusion again.

The rendered table is [`results/repeat_report.md`](../results/repeat_report.md).

## Results

| Scenario | Runs | PASS | Target error min/mean/max (m) | Clearance min/max (m) | Contacts | Landings |
|---|---:|---:|---|---|---:|---:|
| gate | 5 | **5/5** | 0.133 / 0.489 / 0.783 | 0.810 / 1.176 | 0 | 5/5 |
| gate-double | 5 | **5/5** | 0.167 / 0.260 / 0.350 | 0.544 / 0.708 | 0 | 5/5 |
| gate-target1, original 0.5 m / 0.2 m | 3 | **0/3** | 0.364 / 0.393 / 0.408 | 0.018 / 0.384 | **4** | 3/3 |
| gate-target1, 0.8 m / 0.1 m | 10 | **9/10** | 0.043 / 0.287 / 0.612 | 0.667 / 0.776 | **1** | 10/10 |
| gate-target1, margin 1.0 m / 0.05 m | 20 | **16/20** | 0.133 / 1.191 / 7.190 | 0.469 / 0.943 | **186** | 16/20 |

The progression is the point:

- **0.5/0.2** failed **0/3**; 4 contacts, minimum 0.018 m.
- **0.8/0.1** improved to **9/10**; one contact at 0.704 m reported clearance.
- **1.0/0.05** looked like **10/10**, but the next ten runs produced 4 failures:
  - runs 15, 16 and 18 timed out without reaching target_1 (errors 7.190, 1.781,
    2.523 m; zero contacts);
  - run 17 had a catastrophic gate strike: **186 contacts**, target error
    6.834 m, landing row target 0.
- **n=20 is 16/20.** The 1.0/0.05 configuration is not robust. This release makes
  no new tuning claim; the target1 task is downgraded to ⚠️.

The earlier samples (0/3, 9/10, the first 10/10 runs) are preserved in
`results/repeat/`; none of the failures are hidden.

## What is verified, and what is not

| Claim | Status | Evidence |
|---|---|---|
| gate 5/5 repeats | ✅ verified | 0 contacts, 0.810 m minimum |
| gate-double 5/5 repeats | ✅ verified | 0 contacts, 0.544 m minimum |
| gate-target1 margin 10/10 | ❌ **not repeatable** | 16/20 at n=20; 4 failures |
| gate-target1 0.8/0.1 | ⚠️ **9/10** | one contact |
| gate-target1 original 0.5/0.2 | ❌ **0/3** | 4 contacts |
| Target1 scenario as a whole | ⚠️ **16/20, two failure modes** | timeout + catastrophic contact |
| Larger sample / confidence interval | ❌ **not done** | n=20 target1, n=5 others |
| Hardware / real sensor | ❌ **not done** | SITL, ideal depth |

## Evidence

- `results/repeat_report.md` and `results/repeat_report.json` — the table above.
- `results/repeat/<scenario>_<n>_summary.json` — 43 per-run reports (5 + 5 + 3 +
  10 + 20).
- `results/repeat/<scenario>_<n>_landing.csv` — per-run landing row.
- `results/repeat/*.log` — per-run offboard/depth logs (kept locally; not all
  copied into git).

## Reproducing it

```bash
make repeat5             # gate, gate-target1 (margin), gate-double 5x
make repeat-target1-20   # twenty runs of the margin gate-target1 mission
```

The target1 mission is `config/mission_gate_target1.yaml` (1.0 m inflation,
0.05 m waypoint tolerance). The 0.8/0.1 and 0.5/0.2 samples are historical
evidence and are not regenerated by these targets. n=20 is still SITL-only; the
timeout and 186-contact failures are not explained by a single margin number.
